# 委任実行モード(Execution Handoff 3 択化)設計書

日付: 2026-08-05
対象ブランチ: dev(superpowers-light フォーク独自改良)

## 背景と動機

writing-plans の Execution Handoff は現在 2 択(Subagent-Driven / Inline)で、
どちらもメインセッションが実行に拘束され、実行ログでコンテキストを消費する。

本改良は 3 択目「委任実行(Delegated)」を追加する。コントローラ役のサブエージェント
を 1 体ディスパッチし、その中で SDD ループ(実装者・レビュアーの孫エージェント)を
回させる。動機は (1) メインセッションのコンテキスト温存、(2) 将来の
「計画を渡せば完成する」自動化パイプラインへの布石。

実現可能性は検証済み: このハーネスではサブエージェントが Agent ツールを持ち
孫エージェントを起動できる。また agentId への SendMessage で停止中のサブ
エージェントとの対話継続ができる。

## 要件

1. writing-plans の Execution Handoff を 3 択に拡張する:
   1. Subagent-Driven(現行どおり・推奨)
   2. Inline Execution(現行どおり)
   3. Delegated(新設・superpowers-light 独自)
2. 委任モードでは、親セッションはコントローラサブエージェントを 1 体だけ
   ディスパッチする。渡すのは計画ファイルパス、レポートファイルパス、
   テンプレート本文(`delegated-controller-prompt.md`)のみ。**会話履歴は渡さない**。
   モデル指定はコントローラ本体のみ最上位を明示指定する(SDD Model Selection の
   「アーキテクチャ・設計」階層に相当。孫エージェントのモデルはコントローラが
   同 Model Selection に従い階層別に選ぶ)。
3. コントローラは分離ワークツリーを自分で作成し、全作業(ファイル編集・git 操作)
   をワークツリー内に固定する。テンプレートに作業ディレクトリ固定を明示的に
   指示する(親リポジトリの checkout を直接触ることの禁止を含む)。
   **ワークツリーは常に `git worktree add <リポジトリルート>/.worktrees/<決定的名>`
   で作成する**。決定的名は計画ファイル basename から拡張子を除き `sdd-` を前置した
   もの(例: 計画 `2026-08-05-foo.md` → `sdd-2026-08-05-foo`)。ブランチ名は
   ワークツリー名と同名とし、DONE 報告で実名を伝える。
   委任モードではネイティブワークツリーツールも using-git-worktrees も使わない:
   それらの利点(ハーネス連携・自動掃除)は、掃除を親が統合後に行う委任モードでは
   意味を持たず、経路を一本化すれば配置式 1 つ・発見 1 パスで済むため。
   これにより親は報告を待たずにワークツリーパスを計算できる。同名ワークツリーが
   既に存在する場合は新規作成せず再利用し、中のレジャーを確認して途中から再開する
   (これが障害回復の経路になる)。
   delegated-controller-prompt.md にこの指示を明記し、委任モードでは
   using-git-worktrees を経由しないことを SKILL.md 追記側にも記す。
4. コントローラは subagent-driven-development の SKILL.md を読み、その手順
   (タスクごとの実装者ディスパッチ、二段レビュー、フィックスループ、レジャー、
   最終レビュー)に従って計画を実行する。**ただし統合(マージ/PR)は行わない**:
   最終ブランチレビューとその修正までがコントローラの責務で、
   finishing-a-development-branch は実行しない。統合判断は人間のものなので、
   DONE 受領後に親セッションがユーザーと finishing-a-development-branch を実施する。
5. コントローラが親に返すステータスは 3 種のみ:
   - **QUESTION** — 人間の判断が必要な場面(計画矛盾の裁定、フィックスループ
     5 周超過で load-bearing な欠陥、BLOCKED、実装者からの要回答質問で
     コントローラが自力裁定できないもの)。質問文・選択肢・文脈を添えて停止する。
   - **DONE** — 全タスクと最終ブランチレビュー(およびその修正)が完了。
     ブランチは未統合のまま。コミット一覧、レビュー結果要約、保留(parked/deferred)
     事項、ブランチ名とワークツリーパスを報告する。
   - **FAILED** — 環境レベルの継続不能な失敗に限る(ワークツリー作成不能、
     リポジトリ破損、必要ツールの喪失など)。レジャー上の到達位置と原因を報告する。
     **QUESTION と FAILED の判断に迷う場合は常に QUESTION を選ぶ**(人間が裁ける
     余地を残す)。
6. **レポートファイル契約**: パスは親が決めてディスパッチ時に渡す。既定の導出式:
   `<ワークツリー>/.superpowers/sdd/<計画 basename>/delegated-report.md`
   (「ワークスペース」= SDD がワークツリー内に作る計画別ディレクトリを指す。
   要件 3 の分離ワークツリー全体とは区別する)。
   コントローラは DONE/FAILED 時に詳細(コミット一覧・各タスクのレビュー結果・
   保留事項・QUESTION の往復記録)をこのファイルに書き、親へのステータス
   メッセージは 15 行以内の要約に留める(SDD の実装者レポート契約と同型)。
   QUESTION 時はファイル更新不要。FAILED 時にワークツリー自体が存在しない
   場合は、レポートファイルのパスを作成せず詳細をステータスメッセージ本文に
   含める(残骸ディレクトリが再ディスパッチの git worktree add を塞ぐのを
   防ぐため)。コントローラは DONE 後もワークスペースと
   レジャーを削除しない(統合完了後の掃除は親側の責務)。
7. 親セッションは QUESTION をそのままユーザーに取り次ぎ、ユーザーの回答を
   SendMessage で同じコントローラに返す。コントローラは文脈を保ったまま再開する。
8. 進捗の逐次報告は行わない(QUESTION と DONE/FAILED のみ)。
9. 障害回復: コントローラの SDD レジャーは子ワークツリー内に残る。コントローラ
   喪失時は、新しいコントローラを同じ計画で再ディスパッチする。ワークツリー名は
   計画ファイル名から決定的に導出されるため(要件 3)、新コントローラは既存
   ワークツリーを発見・再利用し、レジャーから途中再開する。親はコントローラの
   agentId を控える(再開の第一手段は SendMessage、それが不能なら再ディスパッチ)。
   **喪失の判断基準**: SendMessage がエラーを返す、またはハーネスがエージェントの
   終了・失敗を通知した場合。能動的な死活監視は行わない。
10. 編集は追記中心とし、フォーク独自箇所には「(superpowers-light addition)」
    マーカーを付ける。Execution Handoff の 2 択提示文は 3 択への書き換えを許す
    (このセクションのみ書き換え対象)。

## 検証方法

1. **理解度テスト**: サブエージェントに変更後の各ファイルを読ませ、
   (a) 委任時に誰が何をディスパッチするか、(b) 渡すもの/渡してはいけないもの、
   (c) QUESTION/DONE/FAILED の扱い、(d) 再開・障害回復手順、を正しく読み取れる
   ことを確認する。
2. **実地テスト**: 使い捨てのおもちゃ計画(1 タスク、意図的に QUESTION を誘発する
   曖昧点を 1 つ仕込む)を委任モードで実行し、以下を確認する:
   (a) コントローラが孫エージェントで実装すること
   (b) QUESTION が親に返り、回答を SendMessage で返すと再開すること
   (c) DONE 報告(コミット・レビュー結果・ブランチ名・ワークツリーパス)が返り、
       ブランチが未統合のままであること
   テスト成果物はテスト後に破棄する。

## スコープ外

- executing-plans の変更
- 複数計画の並行委任
- 進捗のリアルタイム監視機構
