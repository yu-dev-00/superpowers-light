# サブエージェント・ドキュメントレビュー導入 設計書

日付: 2026-07-31
対象ブランチ: dev(superpowers-light フォーク独自改良)

## 背景と動機

upstream はかつてスペック・計画のサブエージェントレビューループを持っていたが、
コミット e6221a4(2026-03)で「実行時間を約2倍にする割に品質指標が改善しない」
という実測に基づきインラインのセルフレビューへ置き換えた。

一方、本フォークの利用者の経験では、別セッション(フレッシュコンテキスト)による
レビューで実際にミスが多く見つかっている。書き手のセッションはスペックの誤読を
文脈ごと抱えるため、読み返しても同じ誤読をなぞる。フレッシュコンテキストには
このアンカーがない。upstream の測定は「セルフレビュー比の上乗せ」を粗い指標で
測ったものであり、本フォークの利用条件を代表しない、と判断した。

そこで、**セルフレビューを残したまま**(二段構え)、その後にサブエージェント
レビューを無条件で追加する。

## 要件

1. brainstorming のスペック作成後、および writing-plans の計画作成後に、
   サブエージェントによるドキュメントレビューを必ず実施する(無条件)。
2. 既存のインラインセルフレビューは変更せず残す。サブエージェントレビューは
   セルフレビュー(および修正)の完了後に行う。
3. レビュアーには会話履歴を渡さない。渡すのはレビュー対象ファイルのパスのみ
   (計画レビュー時は参照用にスペックのパスも渡す)。
4. 指摘があればメインセッションが修正し、全体を再ディスパッチ。最大 3 周で
   収束しない場合はユーザーにエスカレーション。レビュアーの指摘は助言扱いで、
   書き手が根拠を示して不同意を表明してよい。
5. レビュー結果はチャットに要約表示し、「セルフレビュー通過後に見つかった指摘」
   であることが利用者に分かるようにする(上乗せ効果の継続観察のため)。

## レビューフロー(両スキル共通)

```
セルフレビュー(既存・インライン修正)
  → サブエージェントレビュー(general-purpose、対象ファイルパスのみ渡す)
  → Issues Found: メインセッションが修正 → 全体を再ディスパッチ(最大 3 周)
  → 3 周で収束しない場合: ユーザーにエスカレーション
  → Approved: 既存の次ステップへ
      - brainstorming: ユーザーレビューゲート
      - writing-plans: 実行ハンドオフ
```

## レビュアープロンプトの要点

旧テンプレートの構造を踏襲する:

- チェック観点表(Completeness / Spec Alignment / Task Decomposition / Buildability。
  スペック用は Completeness / Internal Consistency / Ambiguity / Scope)
- キャリブレーション: 「実装(実行)時に実害が出る問題だけを指摘せよ。文体の
  好みや nice-to-have は指摘しない。深刻なギャップがない限り承認せよ」
- 出力形式: Status(Approved | Issues Found)/ Issues / Recommendations(助言)

追加調整(本フォーク独自):

- 「このドキュメントはセルフレビュー通過済みである。表面的な問題より、書き手が
  自分では気づけない類の問題 — スペックの誤読、内部矛盾、暗黙の前提 — を重点的に
  探せ」という指示を加える。

## 検証方法

writing-skills スキルの手順に従い、使い捨てのテストシナリオ(小さな架空機能)で
brainstorming → writing-plans を通しで実行し、以下を確認する:

1. スペック作成後・計画作成後の両方でレビュアーが確実にディスパッチされる
2. レビュアーへのプロンプトに会話履歴が含まれていない
3. 指摘 → 修正 → 再レビューのループが回り、承認後に次ステップへ進む

## スコープ外

- subagent-driven-development など他スキルの変更
- レビュー結果の永続ログ(チャット観察で不十分と分かったら別途検討)
- 条件付きディスパッチ(閾値判定)— 無条件導入で開始し、コストが問題になったら検討
